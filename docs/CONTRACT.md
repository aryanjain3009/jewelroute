# JewelRoute API contract (v1) — the single source both apps build against

Base: the NestJS API serves everything under `/v1`. The web app calls it **same-origin** through a Next.js rewrite `/api/:path* → ${API_ORIGIN}/:path*`, so the browser always calls `/api/v1/...` and auth cookies are first-party.

- **2026-10-21 (api, fixes for the T3 review `docs/brain/reviews/2026-10-21-audit-api-review.md` — tests A15, A17, A20, A21, E1–E2, L1–L2; migrations `…1100`–`…1300`)** — supersedes the round-2 grace-window and self-ack wording below:
  - **Refresh grace is one reuse, same successor.** A rotated refresh token presented again within 30 s **with the same user agent** returns the **same** successor refresh token it was rotated into (and a fresh access token) — exactly once. A second reuse, another user agent, reuse after 30 s, or a logged-out token is theft: every live refresh token of the user is revoked → `401 INVALID_REFRESH_TOKEN`. Two tabs therefore end up on one session.
  - `POST /v1/auth/logout` revokes **only the presented session** (other devices stay signed in). **New** `POST /v1/auth/logout-all` (authenticated, no body) → `200 {}`: revokes every refresh token of the caller and clears `jr_at`/`jr_rt`.
  - **Device cookie `jr_dev`.** Login sets an httpOnly, `SameSite=Lax`, 365-day random device id (kept across logins when the browser already has a valid one; survives logout). Only its sha256 is stored, on the session row. **Self-ack triggers are now the agent's session (`AGENT_SESSION`) or that device cookie (`AGENT_DEVICE`) on the ack request / code page — never IP or user agent**, which remain stored evidence only. Field names are unchanged (`selfAckSuspected`, `selfAckReason`, `ACK_SELF_SUSPECTED`).
  - **Retention:** the cron sweep (`/v1/internal/dispatch`, also ≤ 1/min post-commit) deletes refresh tokens expired or revoked more than 30 days ago and clears `Memo.ackIp/ackUserAgent` 90 days after the ack (or after the memo when the link was only viewed); the self-ack finding is kept. Run stats add `tokensPurged`, `evidenceCleared`. The retailer user agent is no longer copied into the `memo.ack` audit row.
  - **Webhook URLs:** the built-in receiver is exempt only for the exact `API_PUBLIC_URL` origin and path `/v1/dev/webhook-receiver/<[A-Za-z0-9_-]{1,100}>` (no `..`, encoded slashes, query, fragment or credentials). 6to4 (`2002::/16`), NAT64 local-use (`64:ff9b:1::/48`), Teredo (`2001::/32`) and `100::/64` are refused too. `422 WEBHOOK_URL_FORBIDDEN` and blocked attempts use one generic message ("This URL cannot receive webhooks — use a public http(s) address" / "Blocked: destination is not a public address (SSRF guard)") — no resolved addresses. DNS lookups time out after 3 s. `WEBHOOK_ALLOW_PRIVATE=true` is ignored in production except for demo-mode tenants.
  - `POST/PATCH /v1/admin/shops`: an empty or blank `ownerName` / `phone` is stored as `null` (create and PATCH alike).

## v3 — credit-aware orders, receivables, one activity model (2026-10-21, **implemented** — exact shapes and the open decisions are in the Changelog entry "api, v3")

**Order approval is a rule, not a default.** Order statuses become: `CONFIRMED` (no approval needed — the normal case), `PENDING_APPROVAL` (a rule tripped), `APPROVED` (manager approved a pending order), `REJECTED`, `CANCELLED`, plus the existing `DRAFT`. Legacy `SUBMITTED` rows are migrated: those that would trip a rule → `PENDING_APPROVAL`, otherwise `CONFIRMED`. Approve/reject only from `PENDING_APPROVAL` (`409 ORDER_NOT_PENDING` otherwise).
- Rules (server-authoritative, evaluated inside the create transaction with the shop row locked, recorded on the order):
  1. `CREDIT_LIMIT` — projectedExposure > creditLimit (when creditLimit > 0).
  2. `ORDER_THRESHOLD` — order total ≥ tenant `approvalThresholdPaise` (when set).
- Exposure model (`CreditPosition`): `outstandingPaise` = Σ total of the shop's `CONFIRMED`+`APPROVED` orders not yet settled (`settledAt` null) **+** the shop's opening balance (`Shop.openingOutstandingPaise`, seeded) ; `memoExposurePaise` = Σ value of OUT memo items at the shop; `exposurePaise` = outstanding + memoExposure; `creditLimitPaise`; `availableCreditPaise` = max(0, limit − exposure); and for a prospective order `orderAmountPaise`, `projectedExposurePaise` = exposure + orderAmount, `requiresApproval`, `reasons: ('CREDIT_LIMIT'|'ORDER_THRESHOLD')[]`.
- `GET /v1/visits/:id/credit?amountPaise=` (agent, own open visit) and `GET /v1/admin/shops/:id/credit?amountPaise=` → `CreditPosition` — the order review shows it before placing.
- `POST /v1/orders` response adds `order.approval: { required: boolean, reasons: string[], position: CreditPosition /* frozen at creation */ }` (also on order reads).
- `POST /v1/admin/orders/:id/settle` → marks an order paid/settled (`settledAt`, audited, event `order.settled`) — reduces outstanding. `POST /v1/admin/orders/:id/cancel` (CONFIRMED/PENDING only, audited, `order.cancelled`).
- Tenant settings: `GET/PATCH /v1/admin/settings` → `{ approvalThresholdPaise: number|null, demoMode }` (audited).
- Webhook events add `order.pending_approval`, `order.confirmed`, `order.settled`, `order.cancelled` (`order.created` still fires for every order).
- `ShopRow` / shop record add `credit: CreditPosition` (no prospective order), `upcomingVisit`, `lastOrder`.

**One activity model.** Every business event is an `OutboxEvent` that also stores indexed refs: `shopId?, agentId?, visitId?, orderId?, memoId?, pieceIds[]` (new columns, back-filled from payloads in the migration). `ActivityItem` adds `refs: { shop?, agent?, visit?, order?, memo?, pieces?: {id,tagCode}[] }`, `kind` (`visit|order|memo|custody|proof|ack|rate|webhook|system`) and an optional `detail` (photo url / amounts / from→to) so every surface renders the same event the same way. Single endpoint: `GET /v1/admin/activity?shopId=&agentId=&visitId=&orderId=&memoId=&pieceId=&before=&limit=` (cursor by createdAt+id); record endpoints' `activity` arrays use the same projection. No surface builds its own feed.

**Custody ledger rows** (`CustodyEventRow`) add `ack?: { status, method: 'QR_CONFIRM'|'OTP', at, by: 'retailer' }` for memo hand-overs, and `order?: {id, number}` for conversions — so a sample record answers "who acknowledged receiving it".

## Conventions
- Envelope: success `{ "ok": true, "data": ... }`; error `{ "ok": false, "error": { "code": "STRING_CODE", "message": "...", "details"?: any }, "requestId": "..." }` with a matching HTTP status.
- Money: integer **paise** as JSON numbers (fields end in `Paise`). Weight: integer **milligrams** (fields end in `Mg`). Distances in metres (`...M`). Dates ISO-8601 UTC; business dates `YYYY-MM-DD` in Asia/Kolkata.
- Auth: login sets httpOnly cookies `jr_at` (access JWT, 15 min) and `jr_rt` (refresh, 30 days, rotating). `Authorization: Bearer <jwt>` also accepted. On 401 `TOKEN_EXPIRED`, call `POST /v1/auth/refresh` once, then retry.
- Every mutating field-agent call that creates something (`check-in`, `orders`, `memos`, `memos/:id/return`, `proofs`) takes header `Idempotency-Key: <uuid>`; replays return the original response; same key + different body → `422 IDEMPOTENCY_KEY_REUSED`.
- Tenant is taken from the token. Every query is tenant-scoped server-side.
- Roles: `FIELD_AGENT`, `ADMIN`. `/v1/field/*`, `/v1/visits/*` = agent (admin may read). `/v1/admin/*` = admin.
- Request id: response header `x-request-id`.

### Delivery format
```
POST <endpoint url>
Content-Type: application/json
User-Agent: JewelRoute-Webhooks/1.0
X-JewelRoute-Event: order.created
X-JewelRoute-Delivery: <deliveryId>
X-JewelRoute-Timestamp: <unix seconds>
X-JewelRoute-Signature: sha256=<hex HMAC-SHA256(secret, `${timestamp}.${rawBody}`)>

{ "id": "evt_01J...", "type": "order.created", "tenantId": "aurum", "createdAt": "...", "data": { ... } }
```
Retries: **1 immediate attempt + 6 retries** (7 attempts total) with backoff 30s, 2m, 10m, 30m, 2h, 6h; after the 7th failure the delivery is `DEAD`. 2xx = success. Idempotent by `id`. Every attempt is logged with the exact `requestHeaders` sent (signature included, never the secret).
