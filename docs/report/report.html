Contents

    1Summary

    JewelRoute is a field-sales system for jewellery makers who sell through retailers. A manager plans routes; field agents visit shops, check in with server-verified GPS, attach a photo, book orders priced from the live gold rate, and leave physical samples on memo (consignment) with a retailer who acknowledges receipt from their own phone. Every custody move of every sample is recorded in an append-only ledger, and state changes are published to customer systems as signed webhooks.

    Two apps, one contract

    • Web (apps/web, Next.js 15): three surfaces in one app. The field app at /field/* is mobile-first (Today, Visits, Catalog, Profile tabs). The admin console is at /admin/* (Home, Visits, Agents, Shops, Orders, Memos, Samples, Catalog, Integrations, Settings). The public retailer acknowledgement page is at /ack/[token]. There are also a marketing page at / and /developers docs.
    • API (apps/api, NestJS 11 + Prisma): all business rules, pricing, custody, idempotency, tenancy and webhooks. PostgreSQL is the single source of truth. The web never patches derived state locally: it writes, then refetches.
    • Shared (packages/shared): pricing maths (priceDesign, orderTotals), the geofence decision, IST business dates, money formatting and the webhook event list. The API uses them as the authority and the web uses the same code for display only.

    How they talk

    Browser → same-origin /api/v1/… → Next.js rewrite in apps/web/next.config.ts (/api/:path* → ${API_ORIGIN}/:path*) → NestJS /v1/* (throttler → auth/RBAC guard → zod validation → service in a Prisma transaction) → PostgreSQL. Responses come back in one envelope, {ok:true,data} or {ok:false,error:{code,message,details},requestId}. Auth is two httpOnly first-party cookies (jr_at access JWT, 15 min; jr_rt rotating refresh token, 30 days), so the browser sends them with no CORS. State changes also write an OutboxEvent row in the same transaction. After the response, a post-commit interceptor kicks the dispatcher, which fans events out to subscribed endpoints as HMAC-signed HTTP POSTs with a retry ladder.

    2Architecture and connection

    One browser-visible origin (the Next.js app) fronts the API. Cookies stay first-party, the browser never needs CORS, and the API remains independently deployable (on Vercel, apps/api/vercel.json routes every path to one serverless function that boots Nest once per instance, see src/serverless.ts).

    The request path

    1. Browser: every authenticated call goes through api() in apps/web/src/lib/api.ts. It prefixes /api/v1, sets credentials:"include" and cache:"no-store", JSON-encodes the body (or passes FormData), and adds Idempotency-Key when asked (true → fresh crypto.randomUUID(), or a caller-supplied stable key).
    2. Next.js: next.config.ts rewrites /api/:path* to ${API_ORIGIN}/:path* (default http://localhost:4000) and adds security headers to every page (X-Content-Type-Options, Referrer-Policy, X-Frame-Options: SAMEORIGIN, Permissions-Policy: camera=(self), geolocation=(self)).
    3. Middleware (src/middleware.ts, matcher /field/:path* and /admin/:path*): a cheap gate that redirects to /login?next=… when neither jr_at nor jr_rt is present. It does no verification; real authorization happens in the API on every call. After login, login-form.tsx sends ADMIN users to /admin and FIELD_AGENT users to /field/today, and honours ?next= only inside the role's own area.
    4. NestJS (src/app.ts): helmet, cookie-parser, 1 MB JSON limit, CORS allowlist (a fallback, since the proxy makes calls same-origin), pino request logging. Then the global guards, handler, interceptors and exception filter described below.

    Authentication and session refresh

    LoginPOST /v1/auth/login looks the user up by email (optionally scoped by tenantSlug; an email that exists in two tenants without a slug fails), compares with bcrypt, and compares against a dummy hash when the user is missing so timing does not reveal existence. It issues an access JWT and a refresh token, sets both cookies, and also returns them in the body for API clients and the e2e script.
    Access token (jr_at)JWT signed with JWT_ACCESS_SECRET, issuer jewelroute, 15 min. Claims: sub (user id), tid (tenant id), tslug, role, name. Cookie flags: httpOnly, SameSite=Lax, Secure in production, path /. AuthGuard also accepts Authorization: Bearer. An expired token gives 401 TOKEN_EXPIRED; a bad one gives 401 INVALID_TOKEN.
    Refresh token (jr_rt)Opaque rt_<32 random bytes>, stored only as SHA-256 in RefreshToken, 30 days. /auth/refresh claims the row with a conditional updateMany … revokedAt:null, so a token can be used once. Presenting an already-revoked token revokes every live token of that user (theft signal).
    Client refresh on 401In api(), a 401 on any non-/auth/* path triggers a single-flight POST /api/v1/auth/refresh (concurrent 401s share one promise) and one retry of the original call. If the refresh fails, the browser goes to /login?next=<current path>. The XHR upload path (proof-upload.ts) calls api("/auth/me") on 401, which runs the same refresh, then retries the upload once.
    LogoutPOST /v1/auth/logout revokes the presented refresh token and clears both cookies. Deactivating an agent (PATCH /admin/agents/:id {active:false}) revokes all their refresh tokens, but an issued access JWT stays valid for up to 15 min (documented known gap).

    Envelope, error codes and request ids

    • Success: {"ok":true,"data":…}. api() returns json.data.
    • Error: {"ok":false,"error":{"code":"OUTSIDE_GEOFENCE","message":"…","details":{…}},"requestId":"req_01J…"}. api() throws ApiError(status, code, message, details, requestId), and screens branch on code (catalogue in §3.4).
    • Request ids: a client-supplied X-Request-Id matching ^[A-Za-z0-9._-]{6,100}$ is kept; otherwise the API mints req_<ULID>. The id is echoed in the x-request-id response header (exposed via CORS), included in every error body, attached to log lines, and stored on AuditLog.requestId.
    • Retries in the browser: the TanStack default (components/providers.tsx) never retries a 4xx and retries 5xx or network errors up to twice. Default staleTime is 10 s, with refetchOnWindowFocus on.

    Idempotency keys

    IdempotencyService.run() (core/idempotency.ts) inside one Prisma transaction:

    1. Insert (tenantId, key, userId, fingerprint) into IdempotencyKey with ON CONFLICT DO NOTHING. The fingerprint is SHA-256 of method + path + canonical JSON body. A concurrent duplicate blocks on the unique slot until the first transaction ends.
    2. The winner runs the operation and stores the response body in the same transaction, so the stored response exists only if the effect committed. Errors roll the key back too, so a retry after a failure re-executes (test F6).
    3. The loser reads the committed row. Same fingerprint and user returns the stored response. A different body gives 422 IDEMPOTENCY_KEY_REUSED. A row with no response yet gives 409 IDEMPOTENCY_IN_PROGRESS.

    Second line of defence: orders and memos store the key as clientOpId (unique per tenant). On a unique violation the service returns the existing record. Client side: opKey.for(scope, signature) in components/field/guard.ts persists {sig, key} in sessionStorage per action scope (checkin:<visit>:real|sim, order:<visit>, memo:<visit>, return:<memo>). The same body after a timeout or reload therefore reuses the same key, and a changed body gets a new key. Keys are cleared on success or on a 4xx rejection. Proofs carry their own key inside the persisted PendingProof.

    Tenant scoping and RBAC

    • Every row carries tenantId, and every query filters by the JWT's tid. Foreign ids return 404, never 403, so existence never leaks (tests 6 and F1 build a second tenant through the API and probe every v1 and v2 read and write).
    • Agents see only their own visits, orders, memos and proof files (404 otherwise). Admins can read any record in the tenant, but mutating a visit (check-in, proof, order, memo) requires being the assigned agent, so an admin gets 403 NOT_YOUR_VISIT.
    • Permissions are declared per route. Adding a role (for example REGIONAL_MANAGER) is one entry in ROLE_PERMISSIONS.

    Uploads: Vercel Blob or direct

    POST /v1/uploads/proof-token checks that the visit is the caller's and is open, then builds a server-chosen object key tenants/<slug>/visits/<visitId>/<ULID>.jpg.

    • Blob mode (when BLOB_READ_WRITE_TOKEN is set): returns a Vercel Blob client token scoped to exactly that pathname (10 min, ≤8 MB, image types only). The phone uploads with put() from @vercel/blob/client. On attach, the API requires the https URL to contain the object key. Bytes are not re-hashed server-side (documented decision).
    • Direct mode (no token, as in local and self-hosted setups): the phone posts multipart to /api/v1/uploads/direct (≤4 MB). The API validates the type, key shape, tenant and open visit, recomputes SHA-256 and upserts StoredFile (bytea), so a retry is a no-op. It returns url=/api/v1/files/:id. GET /v1/files/:id streams the file: authenticated, tenant-scoped, agents limited to their own visits, Cache-Control: private, immutable, and the SHA-256 as ETag.

    Outbound webhooks

    Events are rows in OutboxEvent written in the same transaction as the change. The payload is exactly the public body {id:"evt_<ULID>", type, tenantId:<slug>, createdAt, data}. The dispatcher (webhooks/dispatcher.ts) has three triggers: the post-commit kick, an opportunistic maybeKick on GET /admin/home, /admin/dashboard and /admin/webhooks/deliveries (at most once per 10 s per instance), and the cron route. Each request is a POST with headers X-JewelRoute-Event, -Delivery, -Timestamp and -Signature: sha256=HMAC_SHA256(secret, "<timestamp>.<raw body>"), a 10 s timeout and redirect:"manual". Endpoint secrets (whsec_…) are stored encrypted with AES-256-GCM under APP_ENCRYPTION_KEY. Pipeline and retry ladder: Figure 9.

    Public acknowledgement page

    Creating a memo returns ack.url = APP_PUBLIC_URL/ack/<token>. The token is 24 random bytes stored only as SHA-256 and valid for 72 h. The agent shows it as a QR code. /ack/[token] renders AckView, which calls the public endpoints with plain fetch (no cookies, no refresh, no redirect). The retailer sees the exact pieces and can tap Confirm receipt, or read a 6-digit code to the agent. The code is HMAC(APP_SECRET, memoId:token) mod 10⁶, shown only while pending and stored only as a hash. Five wrong codes lock code entry with 423 ACK_LOCKED; the QR path still works.

    Versioning: v1 and additive v2

    Every route is under /v1. "v2" is not a URL prefix.     8Sync and consistency

    The backend is the source of truth

    The web holds no derived business state. After a write, it calls useSync()(change), which invalidates every query key in AFFECTS[change] (lib/sync.ts). The server then answers with fresh numbers: bag values, memo exposure, shop status and attention items are all computed server-side. Keys are prefixes, so ["visit"] refreshes every visit query. Local state is limited to drafts and UX: cart, memo picks, notes, the pending photo and idempotency keys in sessionStorage, plus the GPS fix. Pieces in a draft that the server no longer shows in the bag are dropped before submit. Cross-user freshness (agent writes, manager watches, or the reverse) comes from polling and refetch-on-focus:

    Glossary

    MemoConsignment note: physical samples left with a retailer until a due date, then returned or bought. Numbered MEMO-YYYY-NNNNN; acknowledged by the retailer through QR or code.
    Custody / custodianWho physically holds a sample right now: the VAULT, an AGENT (their "bag"), a SHOP (on memo), SOLD or LOST. Changes only through the append-only CustodyEvent ledger.
    Sample piece · tag codeOne physical copy of a design, identified by a tag such as AJ-S-000123, with its own gross and net weight.
    Design · SKUA catalog item (for example a 22K bangle) that defines purity, standard weights and pricing components.
    PurityGold fineness in karats: K24 (≈99.9%), K22 (≈91.6%), K18 (75%), K14 (≈58.5%). Each purity has its own daily rate per gram.
    Paise / mgInteger units: 1 rupee = 100 paise; 1 gram = 1000 milligrams. Price = net mg × rate (paise per g) ÷ 1000 + making + stones + other, then 3% GST on the order subtotal.
    Making chargeLabour charge, either per gram of net weight (paise per g) or a percentage of gold value (basis points).
    Gross / net weightTotal weight vs. gold-only weight (excludes stones); pricing uses net.
