# Backend decisions (apps/api)

- **Nest 11 + Express, compiled with plain `tsc`** (decorator metadata preserved). `src/main.ts` listens locally; `api/index.ts` is the Vercel function and just `require`s `dist/serverless`, which boots Nest once per instance and reuses the Express handler.
- **Prisma 6.19 with `output = "../generated/prisma"`** so the query engine (`native` + `rhel-openssl-3.0.x`) lives inside `apps/api` and is bundled by `vercel.json` `includeFiles` — avoids the pnpm-symlink "engine not found" failure on Vercel.
- **zod** for every DTO (one `parse()` helper → `400 VALIDATION_FAILED`). Swagger documents routes/tags/headers; body schemas are in CONTRACT.md.
- **Tenant scoping**: `tenantId` only from the verified JWT (`ReqCtx.user.tid`); every query filters by it; other-tenant and other-agent ids return 404 (no existence leak). Tested.
- **RBAC as permissions** (`field`, `admin`, `admin.read`) mapped from roles in `ROLE_PERMISSIONS`; a new role is one map entry.
- **Invariants in SQL** (`prisma/migrations/20261021000000_init/migration.sql`, tail): partial unique index "one CHECKED_IN/ACTIVE visit per agent", partial unique "one OUT MemoItem per piece", CHECK "custodian column matches custodianType", value/weight CHECKs, append-only triggers on GoldRate / CustodyEvent / OrderItem. The only escape hatch is a transaction-local `jewelroute.allow_purge` flag used by the seed to wipe a tenant (DELETE only, never UPDATE).
- **Check-in**: `SELECT … FOR UPDATE` on the visit + status/today/other-open checks + the partial index as the final race guard (unique violation → `ANOTHER_VISIT_OPEN`). Distance recomputed server-side with shared `distanceM`/`geofenceDecision`; accuracy slack capped at 50 m. Check-in must be on the planned IST date (`VISIT_NOT_TODAY`).
- **One shop per route day**: a partial unique index on `Visit(tenantId, shopId, plannedDate)` for non-cancelled rows prevents the same retailer from being assigned to two salespeople on the same business date. The API returns `409 SHOP_ALREADY_ASSIGNED`; cancelled rows remain as audit history and release the slot.
- **Simulated GPS** only when `tenant.demoMode`; stored as `SIMULATED`, shown in feed titles and dashboards — never upgraded to VERIFIED.
- **Custody**: one helper (`CustodyService.move`) locks pieces `FOR UPDATE ORDER BY id`, verifies the current custodian, bumps `custodySeq`, appends a gap-free `CustodyEvent`, writes one `sample.custody_changed` outbox event per move (with all pieces) and an audit row — always inside the caller's transaction.
- **Idempotency**: the `(tenantId,key)` row is inserted first *inside* the business transaction (`ON CONFLICT DO NOTHING`); concurrent duplicates block on the unique slot and then replay the stored response; different body → 422. Errors roll the key back, so retries after a failure re-execute. `clientOpId` (= key) is unique on Order/Memo as a second line of defence. Replays are deep-equal (jsonb may reorder keys).
- **Pricing** is authoritative on the server using the shared `priceDesign`/`orderTotals`; current rate = latest `effectiveFrom <= now()` row (append-only). OrderItem freezes rate id/rate/components; `goldRateSnapshot` per purity. Memo item value = valuation at handover (exposure).
- **Webhooks without Redis/BullMQ**: Vercel can't host a long-lived worker; the Postgres outbox + `FOR UPDATE SKIP LOCKED` claim with a 30 s lease gives at-least-once delivery with safe concurrency at this scale. Triggers: post-commit `waitUntil(dispatcher.runOnce())`, opportunistic on dashboard/deliveries reads (≤1/10 s/instance), `/v1/internal/dispatch` (cron, daily on Hobby). `DispatchQueue` interface is the BullMQ extension point.
- **Backoff**: 1 immediate attempt + 6 retries (30s/2m/10m/30m/2h/6h), then DEAD; manual retry = one more immediate attempt. Each attempt stores the exact request headers sent (signature, never the secret) and the response truncated to 2 kB. Endpoint secrets AES-256-GCM at rest; reveal/rotate audited.
- **memo.overdue** emitted once per memo (`overdueNotifiedAt`, reset when extended), scanned lazily (≤1/min/instance) and on every cron dispatch.
- **Uploads**: Vercel Blob client tokens scoped to one pathname/type/8 MB when `BLOB_READ_WRITE_TOKEN` is set; otherwise direct upload (≤4 MB) into `StoredFile.bytes` with server-side sha256, served at `/api/v1/files/:id` (auth + tenant scoped). Blob-mode proofs are trusted by URL⇄pathname match (no server re-hash — known gap). EXIF is never read.
- **Retailer ack**: QR → public page shows exact pieces and a 6-digit code `HMAC(APP_SECRET, memoId:token) mod 10^6`; only the token hash and an HMAC of the code are stored; 72 h TTL; 5 wrong codes → 423.
- **Auth**: bcryptjs, 15 min access JWT (sub,tid,role,tslug,name), 30 d rotating refresh tokens stored hashed; reuse of a rotated token revokes the user's whole token family. Cookies httpOnly, `sameSite=lax`, `secure` in production, no Domain.
- **Refresh reuse grace (audit review M1, 21 Oct 2026; supersedes "any reuse revokes the family").** A rotated token may be presented ONCE more within 30 s with the same user agent and gets the SAME successor (its plaintext is HMAC-derived from the parent id, so no new session is minted). Everything else is theft and revokes all of the user's live tokens. Rotation, grace, revocation, logout-all and deactivation serialise on a per-user advisory lock. Logout revokes only its own session.
- **Self-ack evidence (audit B8 / review M3).** Read model only. Triggers: the agent's session cookie/bearer or the `jr_dev` device cookie (random, httpOnly, 365 d, hash on the session row) on the ack page/confirm. IP and user agent never trigger (the web rewrite can collapse IPs; Android Chrome UAs are near-identical).
- **Retention (review m6, m7).** The cron sweep deletes refresh tokens expired/revoked > 30 days ago and clears `Memo.ackIp/ackUserAgent` 90 days after the ack (DPDP 2023: retailer IP/UA are personal data); the self-ack finding stays. `User.lastSeen*` is no longer written and is cleared after 90 days (drop in a later contract migration).
- **Rate limits** (in-memory per instance — fine for MVP; Redis store is the upgrade): 600/min default, login 10/min, public ack GET 30/min, POST 10/min, ack verify 20/min.
- **Activity feed** = the outbox itself (`title` derived from type + payload), so the feed and webhooks can never disagree.
- **Doc numbers** `ORD-YYYY-NNNNN` / `MEMO-YYYY-NNNNN` / tag codes via a row-locked `DocSequence` upsert (gap-free per tenant).
- **Dates**: business dates are IST (`istDate`), stored as `@db.Date` at UTC midnight.
- **Helmet CSP disabled** (JSON API; Swagger UI assets come from jsDelivr so `/docs` works in the serverless bundle).
- **Migrations + seed on Vercel** (no 5432 egress from the dev workspace): `build` runs `scripts/migrate-on-vercel.cjs` → `prisma migrate deploy` only when `VERCEL=1` (uses `directUrl`; falls back to DATABASE_URL). The seed is `src/seed/seed.ts` → `runSeed()`, compiled into dist (design images imported as JSON), used by both `prisma/seed.ts` and `POST /v1/internal/seed` (CRON_SECRET). Batched with createMany/createManyAndReturn (~1 s locally). Function maxDuration 60 s.
- **v2 record endpoints** live in one `RecordsController` (`src/modules/records.ts`) that also serves the v1 list routes as strict supersets. Builders (`adminVisitRows`, `pieceRows`, `shopRows`, `custodyRows`, `auditRows`, `attention`) take a batch and resolve relations with a constant number of `groupBy` / `DISTINCT ON` / `IN (…)` queries — never per row.
- **Custody ↔ webhook identity**: `CustodyService.move` pre-allocates the `evt_…` id, stamps it on every `CustodyEvent.outboxEventId`, then emits the outbox row with that id — so a piece's ledger row, the webhook payload `id` and the ActivityItem `id` are the same string.
- **Visit attribution of returns/sales**: memo return/convert happen "in" the caller's open visit at the memo's shop (or an explicit open visit there); otherwise no visit. The memo's original visit is never reused.
- **Idempotency-Key is mandatory** for orders, memos, memo return and convert (`400 IDEMPOTENCY_KEY_REQUIRED`). Check-in and proofs dedupe naturally (one open visit; checksum per visit) and still accept keyless calls.
- **MISSED is persisted** by the dispatcher sweep (PLANNED before today IST → MISSED). No webhook event (not in the event list).
- **Unknown GPS accuracy** is not a perfect fix: no slack and never `VERIFIED` (`LOW_ACCURACY`).
- **`GET /visits/:id` `resume`** is the single server-derived answer to "where am I in this visit" for refreshes and app restarts; there are no server-side drafts (orders and memos are written atomically on submit).
- **v3 approval is a rule, not a default** (`docs/CONTRACT.md` § v3). `POST /orders` and memo convert run one credit rule inside the order transaction: lock the shop row `FOR UPDATE` (`CreditService.position(..., {lock:true})`), sum unsettled CONFIRMED+APPROVED orders + opening balance + OUT memo exposure, and call the pure `creditPosition` (`packages/shared/src/credit.ts`). `CREDIT_LIMIT`: projected > limit (limit 0 = no limit); `ORDER_THRESHOLD`: total ≥ tenant threshold. The position is frozen on the order (`creditSnapshot`), the reasons in `approvalReasons`. Approve, settle, cancel and shop PATCH take the same shop lock, so exposure-changing writes at one shop serialise (V2 in `test/v3.test.ts` is red without the lock).
- **PENDING_APPROVAL orders do not count towards exposure** until approved (the manager's approval is the override and may exceed the limit). Settled orders leave outstanding; cancelled/rejected never count.
- **`SUBMITTED` — expand/contract (lead decision B2, 21 Oct 2026, superseding the first v3 note).** `20261021000300` dropped the value in the same release as the code switch; the T3 review (docs/brain/reviews/2026-10-21-v3-credit-activity.md, R8) showed the real impact: the previous build cannot read **any** order (`Value 'CONFIRMED' not found`) and cannot be rolled back to. That migration is applied and immutable, so `20261021000400_v3_expand_enums` re-adds `SUBMITTED`, `20261021000500` adds CHECK `Order_no_submitted` (NOT VALID) and `20261021000600` validates it. No row may use it. **Correction (re-review n2):** the header of `…0400` (applied — left as is) says the value helps "a still-serving older deployment"; it does not — that client still fails on every CONFIRMED row (R8) and its SUBMITTED writes hit `Order_no_submitted` — and the down script goes through TEXT, so it does not need it either. The value is the inert expand step of expand/contract (it also puts `SUBMITTED` back in the Prisma TS type; no code writes it). A later contract migration drops it.
- **Approve/reject outside PENDING_APPROVAL**: APPROVED/REJECTED keep `409 ORDER_ALREADY_DECIDED` (the web already renders "already approved by …" from it); every other status is `409 ORDER_NOT_PENDING`.
- **Memo-converted orders: cancel is refused, reject un-sells (lead decision B1, 21 Oct 2026).** Cancel stays `ORDER_NOT_CANCELLABLE`. Rejecting a converted PENDING_APPROVAL order runs, in the same transaction, `CustodyService.move` SOLD → the memo's shop with reason `SALE_REJECTED` (append-only CustodyEvent, `sample.custody_changed`, audit), flips the memo items CONVERTED → OUT, recomputes the memo status (closedAt cleared) and writes audit `memo.sale_rejected`; `order.rejected` carries `unsold`. The piece is on memo again, so its value is back in memo exposure and memo return works. SQL guard: deferred constraint triggers `SamplePiece_sold_has_live_order` / `Order_dead_unsells_pieces` — a SOLD piece must be referenced by an OrderItem of an order that is not REJECTED/CANCELLED, checked at commit (convert moves the piece before inserting the order). Settled orders cannot be cancelled. `cancelledAt` + `cancellationReason` were added beyond the contract's column list so an order shows who/when without the audit log.
- **Memo convert is evaluated net of the converted pieces**: the memo items flip to CONVERTED before the order is priced, so the sale is not counted twice (memo value + order total).
- **One activity model**: `OutboxEvent` carries `shopId, agentId, visitId, orderId, memoId, pieceIds[]`, derived by one pure function (`core/event-refs.ts`) inside `OutboxService.emit` and the seed's `feed()`, and back-filled by the same rules in SQL (V9 asserts TS and SQL agree). `ActivityService` (`core/activity.ts`) is the only outbox → ActivityItem projection; Home, `/admin/activity` and every record's `activity` call it with a ref filter. Payload-path JSON filters (`data.shop.id`, `data.to.shopId`, …) were removed.
- **`memo.acknowledged` event added** (not in the v3 list) so the `ack` activity kind has a real source and webhooks learn about retailer acknowledgements. Kind `rate` is reserved: gold-rate changes are audited but still emit no outbox event.
- **`availableCreditPaise` is `null` for a shop without a limit** — "unlimited" must never render as ₹0 (`.claude/rules/web.md`).
- **PATCH bodies have no defaults**: zod 4 keeps `.default()` through `.partial()`, so `PATCH /admin/shops` silently reset an omitted `creditLimitPaise` to 0 (switching the credit rule off) and `PATCH /admin/designs` wiped stone value and images. PATCH schemas are now built from default-free field sets (L0015).
- **Activity-refs back-fill is a batched script, not migration work (lead decision M1).** `backfillActivityRefs` (`src/core/backfill-refs.ts`) keyset-pages rows that carry no ref, 1,000 per transaction, with the same `eventRefs()` the live writes use (no SQL/TS drift); idempotent. It runs after `prisma migrate deploy` in the Vercel build (`scripts/backfill-on-vercel.cjs`, after `tsc`) and in `scripts/run-local.sh`; by hand: `pnpm --filter @jewelroute/api db:backfill-activity-refs`. `20261021000300` (applied, immutable) still contains its inline back-fill and per-order loop — measured 110 s with reads on `"Order"` blocked 107 s at 40k orders / 300k events (review R9), 1.9 s at demo size. Rule from here on: migrations add nullable columns, enum values, cheap DDL and `NOT VALID` checks (validated in a separate migration); data back-fills go in batched scripts. `CREATE INDEX CONCURRENTLY` cannot run inside the transaction Prisma wraps a migration in, so on a non-demo tenant new indexes on big tables ship as their own single-statement migration (or are created by hand first and the migration uses `IF NOT EXISTS`).

## Rollback plan (v3)
- **Script:** `apps/api/prisma/rollback/20261021000300_v3_down.sql` (one transaction; not a Prisma migration). Tested forward → down → forward by `apps/api/test/v3.test.ts` V11.
- **Locks / outage:** the script rewrites `"Order"` twice and `"CustodyEvent"` (the largest table) and drops columns/indexes, all under ACCESS EXCLUSIVE until COMMIT — reads and writes on orders, custody and the activity feed block for a time proportional to the ledger size. Run it in a maintenance window with the API stopped (or in maintenance mode).
- **Steps:** (1) export what will be lost: `SELECT id, number, "settledAt", "approvalReasons", "creditSnapshot", "cancelledAt", "cancellationReason" FROM "Order"` and `SELECT id, "openingOutstandingPaise" FROM "Shop"`; (2) if `20261022000100`/`…0110` (hot-path indexes) are applied, first `psql "$DATABASE_URL_DIRECT" -v ON_ERROR_STOP=1 -f apps/api/prisma/rollback/20261022000100_hot_path_indexes_down.sql` (forgets them; the indexes stay); if `20261022000000_session_timezone_utc` is applied, then `psql "$DATABASE_URL_DIRECT" -v ON_ERROR_STOP=1 -f apps/api/prisma/rollback/20261022000000_session_timezone_down.sql` (it keeps the UTC default); if the final-audit migrations `20261021000900`/`…1000` are applied, then `psql "$DATABASE_URL_DIRECT" -v ON_ERROR_STOP=1 -f apps/api/prisma/rollback/20261021000900_audit_down.sql` (rollbacks run newest first), then `psql "$DATABASE_URL_DIRECT" -v ON_ERROR_STOP=1 -f apps/api/prisma/rollback/20261021000300_v3_down.sql`; (3) redeploy the pre-v3 build (`89ec146` or earlier) — its `migrate deploy` is a no-op because the script removes the v3 rows from `_prisma_migrations`; (4) reseed only if this is the demo tenant.
- **Mapping:** CONFIRMED and PENDING_APPROVAL → SUBMITTED (confirmed orders re-enter the old approval queue); CANCELLED → REJECTED with `rejectionReason = 'Cancelled: <reason>'`; custody reason SALE_REJECTED → ADJUSTMENT (ledger rows kept; the column type is rewritten, which does not fire the append-only row trigger).
- **Data lost:** which orders were settled (`settledAt`), approval reasons and frozen credit snapshots, opening balances, the tenant threshold, OutboxEvent ref columns. v3 outbox rows stay (the old feed titles them by type).
- **Re-forward:** `prisma migrate deploy` re-applies 0300–0800; the 0300 mapping re-evaluates the SUBMITTED rows with the credit rule. Then run `pnpm --filter @jewelroute/api db:check-orphans`: a pre-v3 build rejects SUBMITTED conversions without un-selling them, so the rollback window can create SOLD pieces with no live order (the v3 triggers only guard new transitions). It is read-only and exits 1 when it finds any; repair is a human decision (which shop holds the piece, was it paid).
- **Deploy checklist (every v3+ deploy):** after the build's `migrate deploy` + back-fill, run `db:check-orphans` against the database; non-zero = investigate before calling the deploy done.
- **Lock order (re-review N1):** every write path that takes more than one of these row locks takes them as Memo → Visit → SamplePiece (id order) → Shop → Order. Rejecting/approving a memo conversion locks the Memo and its pieces before the Shop (`OrdersService.lockConversion`), matching memo convert. Shop-first deadlocked reject ‖ convert 11/12 in the reviewer's probe; `test/v3.test.ts` V13 (6 rounds) was red (`409 CONCURRENT_UPDATE`) before and is green after.
- **Guard-trigger indexes (re-review n1):** `OrderItem("pieceId")` and `OrderItem("orderId")`, each `CREATE INDEX CONCURRENTLY IF NOT EXISTS` in its own migration (`…0700`, `…0800`) — a single statement is not wrapped in a transaction block, so CONCURRENTLY applies (verified by `prisma migrate deploy` on jewelroute_test and the scratch DBs in V9/V11); V14 EXPLAINs both trigger lookups onto them.

- **Sessions run in UTC (overnight 22 Oct 2026).** Timestamp columns are `TIMESTAMP(3)` holding UTC; raw SQL compares them with `now()` and with Date parameters (sent as `timestamptz`), both read in the session TimeZone. A Postgres whose default zone was IST (Homebrew on an Indian Mac) fired webhook retries at once, held 30 s leases for 5.5 h and would apply a gold rate scheduled for later. Migration `20261022000000_session_timezone_utc` pins the database default to UTC (no-op on Neon/docker); the API logs an error at boot on a non-UTC session. Not a connection-string `options` flag: PgBouncer-style poolers may refuse that startup parameter.
